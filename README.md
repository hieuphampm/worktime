# Workday — Employee Attendance

Astro SSR attendance management using Supabase Auth and PostgreSQL. The interface is Vietnamese and defaults to `Asia/Ho_Chi_Minh`. All writes and company-wide reports run through authenticated server endpoints; browser code never receives the Supabase secret key.

## Local setup

1. Install Node.js 22+ and the Supabase CLI. Docker is required for the local Supabase stack.
2. Copy `.env.example` to `.env` and fill in a Supabase project URL, publishable key, and server-only secret key. Keep `.env` out of Git.
3. Install packages with `npm install`.
4. Start local Supabase with `supabase start`, then apply the migrations with `supabase db reset`.
5. Start Astro with `npm run dev` and open `http://localhost:4321`.

If developing against a hosted Supabase project, set the three Supabase environment values from a dedicated development project, disable **Allow new users to sign up** in Supabase Auth settings, then apply migrations with `supabase link` and `supabase db push`. Do not use production credentials for local development. The checked-in local Supabase config also disables public signup.

## First administrator bootstrap

There is no public registration or bootstrap endpoint. In a trusted Supabase Dashboard session for the project, create one Auth user under **Authentication → Users** and copy its UUID. Then open the project SQL Editor and run the following transaction after replacing the three placeholders with the Auth user UUID, employee ID, and display name. This procedure refuses to add another administrator if one already exists.

```sql
begin;
do $$
begin
  if exists (select 1 from public.profiles where role = 'ADMIN') then
    raise exception 'An administrator already exists';
  end if;
end $$;
insert into public.profiles(id, employee_id, display_name, email, role, is_active)
select '<AUTH_USER_UUID>'::uuid, '<ADMIN_EMPLOYEE_ID>', '<ADMIN_NAME>', email, 'ADMIN', true
from auth.users where id = '<AUTH_USER_UUID>'::uuid;
commit;
```

If the profile insert fails, remove or disable the newly created Auth user in the dashboard. Subsequent accounts must be created by an administrator from **Nhân viên**. Enter a temporary password of at least 12 characters and deliver it directly to the employee through a secure channel. There is no self-service registration route.

## Attendance rules

- A work date is calculated on the server from the current instant and the `company_settings.timezone` value (initially `Asia/Ho_Chi_Minh`). The unique `(employee_id, attendance_date)` constraint is the final duplicate guard.
- Timestamps are stored as UTC `timestamptz`; display and admin corrections use the company timezone.
- A shift that crosses midnight keeps the local check-in date as `attendance_date`, while checkout may be on the next local day. Duration is calculated from the server timestamps. A manager should correct missed checkout records and statuses in the admin screen.
- Holidays are configurable company-local dates for reporting. No status is inferred from a holiday or from missing check-in/out. Official statuses are only `FULL_DAY`, `HALF_DAY`, and `OFF`, with credits 1, 0.5, and 0.
- Admins can create a status-only attendance record for an employee/date with an audit reason. Employees can still check in against that row; the date uniqueness constraint prevents creating a second row.
- Working start/end times are configuration for policy and future reporting; check-in/out are currently recorded at the actual server time without grace-period rounding or automatic attendance-status assignment.
- Local Supabase Auth uses rotating refresh tokens, a 12-hour maximum session, an 8-hour inactivity timeout, and a 12-hour secure, HTTP-only session cookie. Configure matching session limits in each hosted Supabase project's Auth settings.

## Security and data access

- RLS is enabled on all public application tables. Active employees can select only their own profile, attendance and audit rows. Ordinary authenticated users have no attendance insert/update/delete permissions. Profile updates are limited to display name and department columns.
- The private role helper is `SECURITY DEFINER`, has an empty `search_path`, lives in the non-exposed `private` schema, and checks the server-controlled profile role. Attendance changes are performed by server endpoints only after `auth.getUser()` validates the cookie and a server-side profile lookup verifies an active admin/employee role.
- `SUPABASE_SECRET_KEY` is only read by `src/lib/supabase/server.ts`. Never put it in a `PUBLIC_` variable, browser script, URL, response, or log. Do not use `SUPABASE_SECRET_KEY` as a client key.
- Attendance audit rows are generated by a database trigger and are not writable by app users. Admin correction reasons are copied into the audit log.
- Auth accounts created by admins currently receive a confirmed temporary password. Set and share a unique temporary password securely, and reset it if delivery is uncertain. Password reset and mandatory first-login rotation are not yet part of this version.
- Deactivating an account marks its profile inactive, bans Auth sign-in for 100 years, and uses RLS to block old access tokens from reading profile, attendance, or audit data. Reactivating the account removes the ban.

## Tests and local verification

```sh
npm test
npm run check
npm run build
```

The automated suite covers company-local dates and timestamps, role decisions, duplicate check-in/check-out rules, duration and status-credit calculations, correction validation, and workbook columns and summary totals. Export generation supports up to 100,000 rows but stops at 4.3 MB to fit direct serverless downloads; narrow the date range or employee filter for larger reports. For database-level verification, run `supabase db reset` and use a dedicated test project/local Supabase to exercise RLS as both employee and admin. Never run destructive database reset commands against production.

## Vercel deployment

1. Connect this repository to Vercel and use the Astro framework preset. `@astrojs/vercel` is configured for server output in `astro.config.mjs`; no persistent filesystem is required.
2. Create distinct Supabase development/preview and production projects where practical. Apply the checked-in migrations to each target before deploying the matching app version.
3. In Vercel Project Settings, configure `PUBLIC_SUPABASE_URL`, `PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `COMPANY_TIMEZONE`, `COMPANY_NAME`, and `APP_URL` for Development, Preview, and Production. Only the first two are browser-safe. Keep secrets in Vercel settings, never Git.
4. Disable public signups in Supabase Auth for every project. Admin creation uses the server-only Auth Admin API.
5. Set Supabase Auth **Site URL** and redirect allow-list to the local URL plus each exact Vercel preview/production origin. Set password length to 12 characters, session lifetime to 12 hours, and inactivity timeout to 8 hours. Login uses password auth and does not require open signup.
6. Deploy a preview first and check login, employee check-in/out, admin correction/audit, filters, and Excel download. Promote only after those checks pass.

### Migrations and rollback

Review migration SQL, back up production data, then run `supabase db push` against the explicitly linked target project. Verify the migration list and test the app before promoting a deployment. Migrations are forward-only in production: prepare and review a compensating migration for rollback rather than editing migration history or dropping user data. If an app deployment must be rolled back, confirm schema compatibility with the prior app version first.

## Routes

`/login`, `/admin`, `/admin/employees`, `/admin/attendance`, `/admin/reports`, `/admin/audit`, `/admin/settings`, `/employee`, `/employee/history`, and `/unauthorized`. All privileged APIs repeat server-side authentication and authorization checks independently of page middleware.
